## Purpose

This document is the human-readable contract for the task data model.
It exists so that three audiences agree on the same thing:

1. **The brief** — every field the brief asks for must appear here.
2. **The code** — every field here must be declared in `schema.js`
   and enforced by `validators.js`.
3. **The tests** — every rule here must be asserted in the contract test.

When these three disagree, the code and tests prevail, and this document
is corrected to match. This document is not the source of truth; it is
the **reviewable summary** of the source of truth.

## Schema Table

| Field | Type | Required | Max length | Default | Serialization (JSON primitive) | Source |
|---|---|---|---|---|---|---|
| `id` | string (UUID v4) | yes | 36 | generated at creation | `string` | Workflow: identity required for edit and delete |
| `title` | string | yes | 120 | — (must be provided) | `string` | Brief: required field |
| `description` | string | no | 2000 | `""` (empty string) | `string` | Brief: required field, may be empty |
| `creator` | string | yes | 80 | — (must be provided) | `string` | Brief: required field |
| `assignee` | string | yes | 80 | — (must be provided) | `string` | Brief: required field |
| `createdAt` | string (ISO 8601) | yes | 24 | generated at creation | `string` | Workflow: stable ordering on reload |

**No other fields are stored on a task object.**

### Field notes

- **`id`** — Generated by the store at creation time using
  `crypto.randomUUID()` when available, with an RFC 4122 v4 fallback.
  Never accepted from user input. The store ignores any `id` supplied
  by a caller during creation or update.
- **`title`** — Trimmed before storage. Whitespace-only values are
  rejected as if they were empty, so `"   "` and `""` behave the same.
- **`description`** — Optional. Defaults to empty string, not
  `undefined`, so the view layer never has to null-check before
  rendering.
- **`creator`** and **`assignee`** — Trimmed, required, and length-bounded
  to prevent storage exhaustion and to keep the card layout predictable.
- **`createdAt`** — ISO 8601 with milliseconds and `Z` suffix. Generated
  by the store. Used for stable ordering; the view sorts by this field
  and does not depend on array insertion order.

## Declared Absent

These fields are **plausible additions** that are deliberately **not**
in the schema. Each is listed with the reason, so a future contributor
can see that it was considered and rejected rather than forgotten.

| Field | Reason for absence |
|---|---|
| `updatedAt` | Not requested by the brief. Editing is supported, but the workflow does not display or sort by edit time. Adding it now would create a field that no screen reads — technical debt dressed as future-proofing. It is added the day a requirement names a consumer. |
| `status` | Not in the brief. The brief names create / view / edit / delete. It does not define a status transition model, so a `status` field would imply a workflow the application does not have. |
| `priority` | Not in the brief. It would be a field with no consumer and no ordering rule. |
| `dueDate` | Not in the brief. Tasks are recorded, not scheduled. A date field would invite a date picker, date validation, timezone handling, and overdue-state styling — none of which the brief asks for. |
| `completed` / `done` | Not in the workflow. Tasks are removed when they are no longer needed, not marked complete. A boolean here would create a second way to hide a task from view, which the workflow does not define and the UI does not support. |
| `tags` | Not in the brief. Tags would invite tag input, tag filtering, tag deduplication, and tag-based search — four features the brief does not request. |
| `attachments` | Not in the brief. It would require binary storage beyond `localStorage` (quota management, file type validation, download UX). Out of scope by design. |
| `order` / `position` | Not in the brief. Ordering is derived from `createdAt` at render time; a separate order field would need drag-and-drop UI and a reordering persistence rule. Neither is requested. |

### The rule that governs this list

> **A field enters the schema only when the brief or the workflow names
> a consumer for it.** A field that no screen displays and no operation
> reads is not future-proofing — it is silent scope creep, and it is
> the kind of technical debt that is expensive to remove later because
> stored data depends on it.

If a future requirement names a consumer for one of these fields, the
sequence is:

1. Add the field to `FIELDS` in `src/js/store/schema.js`.
2. Remove it from `FORBIDDEN_FIELDS` in the same file.
3. Add its row to the schema table above.
4. Remove its row from this declared-absent section.
5. Add a migration note (existing stored tasks do not have the field).
6. Add a test asserting the field's rules.
7. Update the form renderer if it is a user field.

Steps 1–2 are the only ones that touch code. Steps 3–7 follow
mechanically. The contract test fails if step 3 or step 6 is skipped.

## Machine-Checkable Form

The authoritative definition lives in `src/js/store/schema.js`. The
TypeScript interface below is a **derived summary** — it is what the
schema module produces, not a separate definition to be maintained in
parallel.

```typescript
/**
 * A task as it exists in the application and in localStorage.
 * Every field is a JSON primitive; no dates, no objects, no nested data.
 */
interface Task {
  /** UUID v4. Generated by the store. Never user-supplied. */
  id: string;

  /** Short name shown on the task card. 1–120 chars after trim. */
  title: string;

  /** Long-form details. 0–2000 chars. Defaults to "". */
  description: string;

  /** Name of the person who created the task. 1–80 chars. */
  creator: string;

  /** Name of the person responsible. 1–80 chars. */
  assignee: string;

  /** ISO 8601 timestamp with milliseconds and Z suffix. */
  createdAt: string;
}
```

### JSON-Schema fragment (for external consumers, if any)

If the task data is ever consumed by a backend or an import/export tool,
this fragment describes the same contract in JSON Schema Draft 2020-12:

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "$id": "https://example.invalid/mars-mission-control/task.schema.json",
  "title": "Task",
  "type": "object",
  "additionalProperties": false,
  "required": ["id", "title", "description", "creator", "assignee", "createdAt"],
  "properties": {
    "id": {
      "type": "string",
      "pattern": "^[0-9a-f]{8}-[0-9a-f]{4}-4[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$",
      "description": "UUID v4, generated by the store"
    },
    "title": {
      "type": "string",
      "minLength": 1,
      "maxLength": 120
    },
    "description": {
      "type": "string",
      "maxLength": 2000,
      "default": ""
    },
    "creator": {
      "type": "string",
      "minLength": 1,
      "maxLength": 80
    },
    "assignee": {
      "type": "string",
      "minLength": 1,
      "maxLength": 80
    },
    "createdAt": {
      "type": "string",
      "format": "date-time"
    }
  }
}
```

The `additionalProperties: false` clause is the JSON Schema equivalent
of the store's unknown-field rejection. It is the same rule expressed in
two forms, so a consumer that reads the JSON Schema reaches the same
verdict as the application.

## Enforcement Map

Where each rule is enforced. If any rule has no enforcement point, it is
a documentation-only promise and should be marked as such.

| Rule | Enforced by |
|---|---|
| All six fields have the correct type | `validateField` in `validators.js` |
| Required fields are present and non-empty | `validateField` in `validators.js` |
| Length limits are respected | `validateField` in `validators.js` |
| `id` is a valid UUID v4 | `validateUuidV4` in `validators.js` |
| `createdAt` is a valid ISO 8601 string | `validateIso8601` in `validators.js` |
| Auto fields cannot be spoofed | `buildTask` and `applyPatch` in `taskStore.js` |
| Unknown fields are rejected | `validateTask` in `taskStore.js` |
| Forbidden fields are rejected | `validateTask` in `taskStore.js` |
| Corrupted stored data does not crash the app | `loadAndRecover` in `taskStore.js` |
| Storage quota failures do not crash the app | `persist` in `taskStore.js` |
| The schema matches this document | `tests/unit/schema.test.js` |

## Change Protocol

When the schema changes, all of the following must change together:

1. `FIELDS` (or `FORBIDDEN_FIELDS`) in `src/js/store/schema.js`.
2. The schema table in this document.
3. The declared-absent table in this document, if the change adds or
   removes a field.
4. The contract test in `tests/unit/schema.test.js`.
5. A migration note for any existing stored tasks.
6. The form renderer, if the field is user-supplied.

The contract test asserts the exact field list. If any of the first four
are missed, the test fails. That failure is the mechanism that keeps
this document and the code from drifting apart.

**Migration note convention:** if a stored task lacks a newly required
field, the store's load recovery filters it out rather than crashing.
When the field becomes required, existing stored tasks must be migrated
or discarded — that decision is recorded here, in the migration note
section, at the time the field is added.

---

## Migration Notes

*None yet.* The schema is at its first version. Existing stored tasks
are assumed to match this schema, because the application has not yet
been used with a different schema in a production context. If stored
data is found that does not match, `loadAndRecover` filters it out and
logs a warning; the discarded entries are not recoverable, which is
acceptable for a single-user local application.

When a schema change occurs, a numbered migration note is added here
with: the change, the reason, the affected tasks, the migration strategy
(transform, default, or discard), and the test that proves the
migration ran.
